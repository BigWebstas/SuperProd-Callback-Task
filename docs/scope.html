The idea in one line

You miss a call. Before you forget, the app has already added Call back Jane Doe (+1 555 0134) to your Super Productivity inbox, with the time and a tap-to-dial link in the notes. Known contacts, spam, and quiet hours are skipped per your rules.

01Call ends TelephonyCallback fires on RINGING → IDLE
→
02Read call log CallLog.Calls, newest MISSED_TYPE row
→
03Apply rules contact filter, quiet hours, dedup
→
04Create task deep link to Super Productivity

Part 1 · Detecting a missed call

Two signals, used together

Neither signal alone is reliable. The plan is to use the call-state change as a trigger and the call log as the source of truth.

Trigger: call-state change

  • API 31+: TelephonyCallback.CallStateListener, registered from a foreground service.
  • API 26–30: PhoneStateListener or a PHONE_STATE broadcast receiver.
  • A missed call looks like RINGING then IDLE with no OFFHOOK in between.
  • Wait ~2 seconds after IDLE so the OS has written the call-log row.

Source of truth: the call log

  • Query CallLog.Calls for the newest row where TYPE = MISSED_TYPE (optionally also REJECTED_TYPE, BLOCKED_TYPE).
  • Read NUMBER, DATE, _ID, and CACHED_NAME.
  • A ContentObserver on the call-log URI is a good backup trigger and catches calls missed while the phone was off or the service was killed.

Contact name

Reverse-lookup the number through ContactsContract.PhoneLookup. Fall back to the raw number when there is no match. Name lookup needs READ_CONTACTS and is optional.

Part 2 · Getting the task into Super Productivity

Four surfaces, and what each is good for

Super Productivity exposes four API surfaces. The deep link is the baseline that always works. The Plugin API is richer and is the recommended path once the plugin is on the phone. Details of the plugin approach are in Part 4; this part covers the deep link, which the plugin path also uses as one of its channels.

The deep link

Superseded by the spike

This section documents the assumed deep link, kept for the record. The spike found it does not exist on the installed Android build — see Spike results at the top of this doc. Do not build against it without re-confirming on a newer SP version first.

# Example the app would fire

val uri = Uri.parse("com.super-productivity.app://create-task").buildUpon()

    .appendQueryParameter("notes", notes)
    .build()
startActivity(Intent(Intent.ACTION_VIEW, uri).addFlags(FLAG_ACTIVITY_NEW_TASK))
Known limits of the deep link

Params are title (required, 300 char max), notes, and projectId only. No tag or due-date param. Short syntax like #tag or @today is stored as literal text, not parsed. It creates one task per call and does its own nothing about duplicates, so dedup is on us.

Must verify in a spike

Does firing the deep link pull Super Productivity to the foreground every time? If it does, capturing 5 missed calls means 5 app switches. Mitigations: batch and fire on screen-off, or check whether SP handles the intent silently. Also confirm the minimum SP version that ships the Android URL scheme.

Picking the target project (deep-link fallback only)

This applies only if the build falls back to the plain deep link. The plugin path in Part 4 gives a live project dropdown with none of this.

The deep link takes a projectId but there is no read action to list projects. With Super Sync and E2EE on, the sync data and the Local File Sync file are all ciphertext to us (Part 3). The one plaintext source is a data export or an automatic backup that Super Productivity writes locally as human-readable JSON, outside the sync layer.

  • In Super Productivity: Settings → Export data, which writes a full-state JSON file. Automatic backups (backups/YYYY-MM-DD.json) are the same format.
  • In our app: a one-time file pick. Or point us at a folder and we read the newest export in it on each settings open.
  • We parse the project entities and fill the dropdown with names. The stored value is the project id, exactly what the deep link wants.
  • Read-only. We never write to SP data.
Trade-offs

The list is a snapshot from the export's date, shown next to the dropdown. A project added in SP after that needs a fresh export. Projects change rarely, so a manual re-export is fine. If that is still too much friction, leave it on Inbox and triage there.

Part 3 · Super Sync is ruled out

End-to-end encryption closes every Super Sync path

Your setup: a self-hosted Super Sync server with E2EE on. The keys live only on your devices. Super Productivity has no access to them, and with E2EE required the clients refuse plaintext uploads and refuse plaintext downloads. Every operation on the server is ciphertext.

IdeaWhy it fails under E2EE
App writes tasks as sync ops The op payload must be encrypted with your key. The app would have to hold your key and reimplement SP's crypto. Rejected.
Server shim appends the op The server cannot encrypt a payload it has no key for. Giving the server your key defeats E2EE. Rejected.
Read-only fetch for the project list GET /api/sync/ops returns ciphertext. Same key and crypto problem, just for reading. Rejected.
Read the Local File Sync JSON That file goes through the same sync layer, so it is encrypted too. Rejected.
What still works

Writing tasks is unaffected. The deep link hands the task to your running Super Productivity app, which encrypts and syncs it the normal way. E2EE never enters our code. A plugin is the other option that sidesteps E2EE, because it runs on the decrypted state inside the app. See Part 4.

Part 4 · Option · a local plugin bridge

A plugin, on the phone, no server

A Super Productivity plugin runs inside the app on the decrypted state, so E2EE is a non-issue for it, and it can do what the deep link cannot: addTask / updateTask with tagIds, dueDay, timeEstimate and projectId, plus live getAllProjects() and getAllTags(). It cannot read the call log or be triggered from outside, so it needs a channel from our app. The plugin API exposes platform: 'android', a TASK_CREATED hook, and PluginAPI.request gated by allowedHosts plus an http permission. Two on-device channels use those, no server involved.

B1 · deep link, then enrich

  • App fires the create-task deep link with a compact marker packed into notes, e.g. sp-cb:{"num":"+15550134","rule":"unknown","id":"…"}.
  • Plugin's TASK_CREATED hook fires, reads the marker, calls updateTask to set project, tags and due day, then strips the marker from notes.
  • Zero network. Fully offline. The only channel is the deep link, so it inherits whatever focus behaviour the spike finds. The marker shows in the note for a second or two.

B2 · loopback HTTP

  • App runs a tiny HTTP server bound to 127.0.0.1 from its foreground service.
  • Plugin declares permissions: ["http"] and allowedHosts: ["127.0.0.1"], and a timer polls it while SP is open. It calls addTask with full fields, then acks.
  • No deep link, no foreground pop, no server. Hinges on PluginAPI.request accepting a loopback host and the Android transport allowing cleartext to loopback. Plausible if that request is proxied through Capacitor's native HTTP, which bypasses the WebView CSP. Unverified.

Both share a plugin config dialog with real <select> dropdowns from getAllProjects() and getAllTags(), config in persistDataSynced, dedup by call id. Precedent: the SP-MCP project is a plugin running a polling loop against a local process.

Latency

The plugin runs only while Super Productivity is open. B1 nudges it open by firing the deep link on each call. B2 is silent, so a task can sit in the phone's local queue until you next open SP. For "call back" tasks that is usually fine. If not, B2 can also post a notification that opens SP on tap.

Recommendation, superseded 2026-08-31. This called for building the plugin bridge with B2 preferred, B1 as fallback, Path A as last resort. The spike ruled out all three — see Spike results at the top of this doc. A new write path is needed before this can be built.

Part 4b · Option raised after the spike

Local REST API, over LAN instead of loopback

Part 2 ruled out the desktop Local REST API (127.0.0.1:3876) because it is Electron-only and the phone app is not the desktop. But E2EE is not the blocker there — the Local REST API runs on the desktop app's own decrypted in-memory state, the same reason the plugin bridge sidesteps E2EE. If a desktop Super Productivity instance stays running and reachable on the same LAN, the phone app could POST to http://<desktop-LAN-ip>:3876/api/tasks with the bearer token directly — no plugin, no deep link, no loopback restriction, because the phone is a normal LAN client talking to a real server, not PluginAPI.request reaching into a WebView sandbox.

Reopens a settled constraint — accepted by the user, 2026-08-31

CLAUDE.md previously settled "no Super Productivity desktop is involved." Building this means accepting a desktop instance must be running whenever a missed call happens, on the same LAN as the phone.

Spiked against a real desktop instance, 2026-08-31

Ran a live SP desktop build (18.x, Linux) with an already-enabled Local REST API and its existing bearer token.

QuestionResult
Is it a real task API, not just sync ops? Yes — GET /tasks, POST /tasks, and DELETE /tasks/:id all confirmed live: created a test task, read it back with full fields, deleted it, verified gone. Plaintext, full decrypted task objects — the doc's original assumption about this API holds.
Does it bind the LAN interface, or only loopback? Loopback only — ss shows 127.0.0.1:3876, never 0.0.0.0, across 8+ app launches in the logs. Every localized in-app string hardcodes http://127.0.0.1:3876 too — this is not a setting, it's fixed in the app.
LAN reachability — confirmed working, 2026-08-31

Reaching the API from another device needs a port-forward on the desktop — socat TCP-LISTEN:PORT,fork TCP:127.0.0.1:3876, an SSH remote tunnel, or an nginx reverse proxy on the LAN interface — ordinary networking on the user's own trusted LAN, not a workaround inside SP itself. The user stood one up and it was tested end to end from the phone itself (real Wi-Fi, not USB/adb): a raw request to the forwarded LAN address returned a live 200 with real task data, and a second machine on the same LAN completed a full POST (201 Created). The forward channel works.

One catch: the Host header

The API rejects any request whose Host header doesn't match what it expects — a request to the LAN IP directly (Host: 192.168.1.82) got 403 FORBIDDEN — Invalid Host header. Setting Host: localhost (bare, no port) on the same TCP connection to the forwarded LAN address passed clean. This is a DNS-rebinding guard baked into the server — the production app must send that literal Host: localhost header on every request regardless of what address or port it actually connects to, or every call gets a 403.

Cleanup needed — real account touched

Proving POST created one real task in the user's live account: "MCB spike LAN test — safe to delete" (id A-7gcTY293I7JJxXHmmXE). The forward stopped answering requests partway through this test (TCP connect still succeeds, no application response) before a follow-up DELETE could confirm removal — check whether it needs deleting by hand once the desktop instance is responsive again.

Part 6 · Reliability

The parts that break in the field

  • Dedup. Keep a Room table of processed CallLog._ID values. Both the state trigger and the ContentObserver can fire for the same call.
  • Retry queue. If the deep link throws ActivityNotFoundException (SP not installed or updating), queue the task and retry with WorkManager backoff.
  • OEM battery killers. Xiaomi, Samsung, Oppo aggressively kill background services. Ship an autostart / battery-optimization guide and detect when the service died.
  • Edge cases. Dual SIM, a call missed during another call, voicemail callbacks, repeated calls from the same number in a short window (collapse into one task).
Widget layout — the xmlns typo that reads as "Can't load widget", 2026-09-01

The home-screen status widget failed to load on every device for days. The layout's root declared xmlns:android="http://schemas.android.com/res/android" — the real URI is .../apk/res/android. aapt2 compiles the file either way, but with the wrong URI it never binds the android: attributes to their framework resource IDs, so at runtime layout_width resolves to nothing and AppWidgetHostView inflation throws "You must supply a layout_width attribute", which Launcher3 surfaces as the generic Can't load widget. Two earlier attempts chased a red herring — a caught, non-fatal "Failed to create idmap" line from the launcher's Material You re-theming pass. Same shape as the LIMIT bug: the broken form looks right and half-works, so it hid. Fix: correct the URI (one character); the compiled tree then shows layout_width(0x010100f4) with its resource id bound.
